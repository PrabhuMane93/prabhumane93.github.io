1. No Room for the Full Row? Hello Online Softmax!

Just a reminder, softmax for one entry xi in a row of N scores:

s(xi) = exi−max NΣj=0exj−max

So, in the last post, we saw that softmax is where the real space complexity in attention shows up. Its formula is structured so that you can't produce a single normalized weight until you have the row's true maximum and its full exponentiated sum, and both of those need every score in that row up front. The previous kernel handled this the straightforward way: materialize the entire S matrix first, then give each thread one row to sweep across three times, re-reading the same values from memory each time:

  • Step 1: find the max.
  • Step 2: exponentiate and sum.
  • Step 3: normalize, dividing every entry by that sum.

That works, but it means holding the full, seq_len*seq_len matrix at once, an O(n²) space complexity that only gets worse as the sequence grows. That's the real problem flash attention has to solve: the need to see the entire row before softmax can even start. Let's see how it does this.

2. Running Max and the Exponentiated Sum and the Correction Factor

The two components of softmax's formula that force us to look at the entire row are its max and its exponentiated sum. So here's the real problem statement: can we find a way to compute the softmax of a vector without going through it three times, the three steps above?

Take the array x = [1, 2, 1, 5]. The goal is to traverse it just once, left to right, maintaining two running numbers as we go: a running max, m, and a running sum, l.

Every later step follows the exact same pattern: compare the running max to the new value, and if it changed, rescale everything accumulated so far by e^(m_old − m_new) before folding in the new term. Generalized across all N elements, the whole algorithm collapses into two passes: one combined pass that builds the running max and sum together in a single read of x, and a second, cheap pass that normalizes using whatever final max and sum came out of the first:

Pass 1 (lines 3–5) is exactly the two running numbers we just traced by hand: one read of the array, updating m and l together, with the correction factor rescaling the old sum whenever a bigger max shows up. Pass 2 (lines 6–7) only happens once m_N and l_N, the true max and sum, are known, dividing every term by the same final l_N. The final running sum, d4 ≈ 1.0864, matches computing softmax directly over all four scores at once: max 5, sum e^(1−5) + e^(2−5) + e^(1−5) + e^(5−5) ≈ 1.0864. Same answer, reached one value at a time, two running numbers carried between them, never all four in memory together.

3. Metal kernel implementation

The fix is to never materialize the whole matrix: split Q into small row blocks, split K and V into small row blocks, and compute attention one small Br × Bc tile at a time, holding only that tile in memory before discarding it.

The tiling scheme itself, before any kernel code: one threadgroup owns one Br-row block of Q for its entire lifetime, loaded once. K and V are streamed in Bc-row blocks, one pair per loop iteration, the same block visiting every threadgroup in turn before the next one loads.

Scoring: Q · KT, one row at a time

Once a threadgroup has its Br-row block of Q cached, and the current iteration's Bc-row block of K loaded, the first real computation is the same Q · KT product from Part 1, just run over this iteration's narrow slice instead of the full row.

It's a plain GEMV: one row of the cached Q tile, a single query vector, multiplied against the whole cached K tile, producing that row's fresh scores for this iteration. The raw dot product only gets normalized by √d_model once it's fully summed, not on every multiply inside the loop, the same scaling from Part 1, just applied at the end of a shorter reduction now. Those scaled scores feed straight into that row's running max and exponentiated sum from Section 2, there's no separate step for it.

Once the scores are in, there's a threadgroup barrier: every thread halts until this iteration's whole tile of S is actually finished, not just its own row. The next step reads across a row's scores, and those were written by several different threads, so nobody can move on until all of them have landed.

Then it's on to the next tile: the next Bc-row block of K and V loads in, and the same row-by-row scoring happens again. If this new tile pushes a row's running max higher, everything already accumulated for that row, the running sum and the output being built up alongside it, gets rescaled by the correction factor before the new scores are folded in. If the max didn't move, the correction factor still gets computed, it's just e^(max−max) = 1, a no-op. There's no special case for "did the max change": the same multiply runs every iteration, it only does real work when it needs to.

That same correction step is also where V comes in: this iteration's scores get multiplied against V and folded into a running output, rescaled by the exact same correction factor as the sum. By the time the loop ends, that running output isn't just bookkeeping, it's the actual attention output, one final division by the row's total sum away from done.

That's the full loop: load once, score and barrier, correct and fold, repeat, until every key has been seen and the running totals are exact. The kernel itself (attention-kernels/flash-attention in metal-llm-kernels) verifies against the same PyTorch reference as Part 1, to the same max_abs_error ≈ 3.725e-9, as accurate as materializing the whole row, without ever holding more than one Br × Bc tile in memory.
